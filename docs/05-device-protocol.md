# ৫. ডিভাইস প্রোটোকল (খসড়া)

MQTT অংশ এখনো বাস্তবে বানানো হয়নি — ডিভাইস ও ব্রিজ লেখার সময় এটাই মূল চুক্তি। বদলাতে হলে এখানে আগে বদলান।

টেলিমেট্রির পেলোড অবশ্য এখনই চালু: MQTT না হয়ে আপাতত সরাসরি HTTP-তে পাঠানো যায় (`POST /api/v1/telemetry`, পেলোড একই)। MQTT ব্রিজ হলে ব্রিজ নিজে এই HTTP এন্ডপয়েন্টেই ডেটা বসাবে।

## ডিভাইসের চাবি (এখনই চালু)

ডিভাইসের সারির `api_key` সেট করা থাকলে টেলিমেট্রি পাঠাতে `X-Device-Key` হেডারে সেই চাবি লাগবে — না মিললে ৪০১। `ENV=production` (বা `REQUIRE_DEVICE_KEY=true`) হলে চাবিহীন বা অচেনা ডিভাইসের টেলিমেট্রি সরাসরি ৪০১ — নইলে চাবি নেই এমন ডিভাইস খোলা (ডেভ ও পুরনো ডেপ্লয়ের জন্য)। আকাশ-ছোঁয়া মান (আর্দ্রতা > ১০০, তাপমাত্রা > ৮৫° ইত্যাদি) ৪০০ দিয়ে ফেরত যায়। মালিক চাবি দেখেন `GET /api/v1/devices/:id/key`-তে; নতুন সিডের ডেমো চাবি: `esp32-gw-1 → dev-key-gw-1`, `esp32-field-1 → dev-key-sensor-1`। নতুন চাবি বানাতে মালিক `POST /api/v1/devices/:id/key` চালান — পুরনো চাবি সাথে সাথে অচল, নতুনটা ফার্মওয়্যারে বসান।

```bash
curl -X POST http://localhost:8082/api/v1/telemetry \
  -H 'Content-Type: application/json' \
  -H 'X-Device-Key: dev-key-sensor-1' \
  -d '{"farm":"my-farm","node":"esp32-field-1","soil_moisture":[44,38,31],"air_temp":28,"air_humidity":78,"tank_level":68,"battery_v":12.6}'
```

## টপিকের নাম

`farm/<farm-id>/...`। `farm-id` প্রতি ফার্মের আলাদা নাম।

| টপিক | দিক | বিষয় |
|---|---|---|
| `farm/<id>/telemetry` | ডিভাইস থেকে সার্ভারে | সেন্সরের রিডিং |
| `farm/<id>/status` | ডিভাইস থেকে সার্ভারে | অনলাইন বা অফলাইন (retained, last will) |
| `farm/<id>/pump/set` | সার্ভার থেকে ডিভাইসে | পাম্প চালু-বন্ধ কমান্ড |
| `farm/<id>/valve/<n>/set` | সার্ভার থেকে ডিভাইসে | জোনের ভালভ |
| `farm/<id>/pump/state` | ডিভাইস থেকে সার্ভারে | পাম্পের আসল অবস্থা |
| `farm/<id>/config` | সার্ভার থেকে ডিভাইসে | সীমা ও সময়সূচি (retained) |

## টেলিমেট্রি পেলোড

```json
{
  "farm": "my-farm",
  "node": "esp32-field-1",
  "ts": 1760000000,
  "soil_moisture": [44, 38, 31],
  "air_temp": 28.0,
  "air_humidity": 78,
  "tank_level": 68,
  "battery_v": 12.6
}
```

- `soil_moisture`: জোন অনুযায়ী শতাংশ, ০ থেকে ১০০।
- `ts`: ইউনিক্স সময় (সেকেন্ড)। ডিভাইসে সময় না থাকলে সার্ভার গ্রহণের সময় বসাবে। সার্ভারের ঘড়ির চেয়ে ৫ মিনিটের বেশি সামনের `ts` ৪০০ দিয়ে ফেরত যায় — "ভবিষ্যতের" রিডিং সবসময় সর্বশেষ থেকে আসল রিডিং ঢেকে দিত; ঘড়ি ঠিক না থাকলে `ts` বাদ দিন।
- ডেটা পাঠানোর ব্যবধান: শুরুতে প্রতি ৬০ সেকেন্ড, ব্যাটারি বাঁচাতে পরে বাড়ানো যাবে।

## কমান্ড

```json
{ "state": "ON", "max_minutes": 20, "request_id": "abc123" }
```

- `state`: `ON` বা `OFF`।
- `max_minutes`: ডিভাইস নিজেই এর পর বন্ধ করবে, সার্ভার ভুলে গেলেও।
- `request_id`: ডিভাইস `pump/state`-এ এই আইডিসহ ফলাফল জানাবে, যাতে ড্যাশবোর্ড নিশ্চিত হতে পারে।

## নিরাপত্তা নিয়ম (ডিভাইসে বাধ্যতামূলক)

1. প্রতিটা `ON` কমান্ডে সর্বোচ্চ সময় থাকবে। না থাকলে ডিফল্ট সীমা প্রযোজ্য।
2. ট্যাংক বা পানির স্তর কম হলে `ON` অগ্রাহ্য।
3. সংযোগ হারালে শেষ সময়সূচি অনুযায়ী চলবে, নতুন `ON` ছাড়া সীমা পার হলে বন্ধ।
4. ওয়াচডগ টাইমার: ফার্মওয়্যার আটকে গেলে রিস্টার্ট, রিস্টার্টে পাম্প বন্ধ।
5. পাম্পের কারেন্ট অস্বাভাবিক হলে (যদি সেন্সর থাকে) বন্ধ।

## সুরক্ষা

- ব্রোকারে ইউজারনেম ও পাসওয়ার্ড, সম্ভব হলে TLS।
- ফার্ম অনুযায়ী আলাদা ইউজার ও টপিকের অনুমতি।
- কমান্ডের টপিকে শুধু সার্ভার লিখতে পারবে।
- ডিভাইসের পাসওয়ার্ড কোডে বসিয়ে GitHub-এ তুলবেন না, আলাদা কনফিগ ফাইলে রাখুন।

## খোলা প্রশ্ন

- ওয়াইফাই না সিম মডিউল (LTE) ফার্মে ভালো? ফার্মে ওয়াইফাই রাউটারের কাছে নোড থাকবে কি না তার ওপর নির্ভর করে।
- একাধিক নোড থাকলে `node` আইডি ও জোনের ম্যাপিং কোথায় রাখা হবে।
